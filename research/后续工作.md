# 背景：RAG 正在变成多源输入

实际 RAG 系统通常不只依赖单一向量数据库，而是同时使用多类知识来源：

- **向量数据库 / ANNS**：从已有知识库中快速召回文档片段。
- **网页检索 / Search API**：补充实时性更强、知识库未覆盖的信息。
- **后处理模块**：过滤、去重、重排、截断，形成最终上下文。

因此，RAG 输入不再是一次性准备好的静态 prompt，而是多个来源异步返回、质量不断变化的上下文流。

---

# 现有工作的局限

已有工作开始关注检索和生成之间的流水线化，但通常只覆盖部分场景：

- **AquaPipe**
  - 主要考虑 ANNS 检索结果不断 update 的场景。
  - 关注质量感知调度，但没有充分覆盖多源输入同时到达的问题。

- **PipeRAG**
  - 主要考虑 append 模型，即新知识块持续追加到上下文尾部。
  - 对同一请求中 append 与 update 共存的支持不足。

- **Stream2LLM**
  - 支持 context streaming 与 prefill overlap。
  - 但单个请求通常只对应一种流式输入范式。

---

# 核心观察

多源 RAG 中，不同知识来源天然对应不同的上下文演化方式：

- **网页检索结果更像 Append**
  - 搜索结果逐条返回，可以稳定追加到上下文末尾。
  - 已返回的网页片段一般不会频繁替换。

- **ANNS 中间结果更像 Update**
  - 检索过程中 top-k 结果可能持续变化。
  - 中间结果可能被后续更相关的 chunk 替换。

- **同一个请求可能同时需要两种范式**
  - 只支持一种范式会浪费流水线化机会。
  - 简单拼接又可能破坏 KV Cache 复用。

---

# 切入点

后续工作的目标：让同一个 RAG 请求中的两类知识来源都可以参与流式 prefill。

- **同时支持 Append 与 Update**
  - 网页结果边返回边追加。
  - ANNS 中间结果边更新边重算必要部分。

- **尽量复用 KV Cache**
  - 避免输入顺序变化导致 cache 被释放。
  - 降低重复 prefill 的计算开销。

- **控制延迟和质量的权衡**
  - 更早启动 prefill，降低 TTFT。
  - 同时评估跳过 rerank / filter 后的质量影响。

# 真实多源 RAG 的处理方式

典型系统会等待多个来源都返回，再统一过滤、去重和 rerank。这样有利于最终上下文质量，但会推迟 LLM prefill 的开始时间。

---

# 流式 Prefill 与后处理的矛盾

如果要支持流式 prefill，系统不能一直等待完整上下文准备完成。

- **等待完整检索结果**
  - 可以全局 rerank、去重和筛选。
  - 但 TTFT 较高，LLM 计算资源可能空闲。

- **边检索边 prefill**
  - 可以隐藏部分检索延迟，提前启动 LLM 计算。
  - 但输入顺序和内容不稳定，会带来 KV Cache 管理问题。

可以把“完整后处理、无后处理”作为一个质量与延迟对比实验。

---

# 多源流式输入的核心问题

先做一个简化假设：

- ANNS 的中间 chunk 结果维护一个大小为 $K$ 的候选集合。
- 随着检索推进，候选集合会不断更新。
- 实际系统中，中间可用结果可能少于 $K$ 个。

如果每次都把当前 ANNS 中间结果和网页结果重新拼接，再交给后端 prefill，就会出现一个关键问题：**输入前缀不稳定**。

---

# 输入顺序变化会破坏 KV Cache 复用

![w:900](assets/多源RAG流式prefill的输入问题.svg)

当 append 与 update 结果混合拼接时，无论按时间顺序、网页在前还是 ANNS 在前，都可能导致已经计算过的前缀发生变化。

前缀一变，后端就很难直接复用原有 KV Cache，只能释放或重算部分 cache。

---

# 举例

比如先Append后Update。比如现在Append是FG,Update是ABCDE，那么上一个时间t，系统已经处理了FGABCDE的prefill，如果现在Append变成FGH，那么整个块就是FGHABCDE，那么Update部分的ABCDE就需要重算。如果是先Update后Append，问题也是一样的，Update部分更新会导致Append部分重算。如果是纯按照Append和Update的新块来的时间排序也是一样的问题，这个就不讲解了。

# 暂时的想法

把这两个模式的chunk分开处理。如果Append部分新来了chunk，就只和以前Append部分的chunk做prefill。比如FG后新来了H，那么H就只关注FG。Update如果更新了，比如ABCDE变成了ABIJK，那么新来的IJK关注FGHAB,因为Append的KV Cache是不会被失效的。但是这样的话注意力的模式其实是被更改了，因为AB的KV Cache其实是没有关注到H的

# 实验主线

指标	意义
Invalidated KV tokens	传统拼接会失效多少 token
Recomputed prefill tokens	实际重复算了多少 token
Wasted GPU time	被失效计算占用的 GPU 时间
TTFT / p95 TTFT	用户侧收益
Throughput under high QPS	系统侧收益
Quality delta	近似注意力带来的输出质量下降

# Update Debounce / Coalescing Prefill

核心逻辑：

如果 update 源频繁变化，那不要每次候选一变就立刻 prefill，而是把 update 放进短暂等待队列，等一小段时间或等变化稳定后，再对最新版本做一次 prefill。
