# 稳定 KV 提前传输的受控实验记录

本轮在相同 NIXL Push 链路上比较 `early_stable_kv_push=true/false`。
两组都消费完整 P/D 输出，不使用 TTFT-only。主要观察 P finish 响应到
proxy 收到 D 首续写 token 的 P90/P95，P99 仅作为探索性尾部指标。
同时报告客户端实际的 finish→D 续写、finish→P 首 token 和完整响应耗时，
避免把交接阶段改善误写成整体延迟改善。

## 部署与固定设置

本轮开始于 2026-10-04，启动与回放均由仓库脚本完成。

| 设置 | 本轮取值 |
| --- | --- |
| P/D | g2c9 的两张 NVIDIA A30；一个 `srun` allocation，每端一张卡 |
| Proxy / replay | g2c14；proxy 地址 `http://g2c14:8000` |
| 模型 | Qwen2.5-3B，服务名 `qwen2.5-3b` |
| 显存比例 | P/D 均为 0.90 |
| KV 池 | 启动日志显示每端 440,144 tokens |
| 注意力与掩码 | `TRITON_ATTN`；Masked Padding 开启 |
| 调度 | TP=1；同步调度；`MAX_NUM_SEQS=64` |
| 请求并发上限 | replay `MAX_CONCURRENCY=8` |
| 到达过程 | 正 QPS 使用 Poisson，随机种子 2026；QPS=0 顺序执行 |
| 来源节奏 | Append interval=0.1 秒；Update interval=0.2 秒 |
| 额外延迟 | 两源 initial delay、source finish delay 均为 0 |
| 完整生成 | `max_tokens=64`，temperature=0，采样 seed=2026 |
| 重复 | 每个设置两轮；第一轮 finish-only→early，第二轮反向 |

同主机双卡结果不能直接代表跨主机网络收益。完整运行中包含所有控制消息、
WRITE、最终接收屏障、D 准入与生成，没有通过人工扣除 CPU 开销构造结果。
原有数据第一轮 finish-only 的开始阶段，P 日志出现一次 `reduce_segments`
首次 JIT 编译提示；该轮请求仍完整保留，不删除个别尾部样本。第二轮交换
顺序后的结果用于检查这一类预热和顺序因素是否改变结论。

## 输入与矩阵

先回放原有 `mix_source_perf_qwen` 的前 128 条，QPS=0，各模式两轮。
原始性能集与 SQuAD 质量集没有改写。

另外离线生成三个独立场景，每场景 128 条，知识总长固定为 2048 tokens：

| Append | 最终 Update | 稳定知识占比 | Append chunk 数 | Update 版本数 |
| ---: | ---: | ---: | ---: | ---: |
| 256 | 1792 | 12.5% | 2 | 5 |
| 1024 | 1024 | 50% | 2 | 5 |
| 1792 | 256 | 87.5% | 2 | 5 |

相邻 Update 完整快照的精确 source-local LCP 均为其长度的 75%。每条请求
具有独有模板标识，跨场景同一编号保持相同问题、模板和随机种子；长度校验
包含 chat template、question、物理 padding 以及 64-token 输出预算。
这些合成输入只用于性能，不具备 SQuAD 标准答案。

三个场景分别回放 QPS=0、1、2，每个单元两轮 A/B，合计 4608 次正式测量
请求提交；原有性能集另有 512 次。这里的“正式测量”仅表示排除预热，
不代表所有提交都成功或统计有效。各场景预热两条路径，预热不进入统计。
不同数据场景与负载单元串行运行，共用同一对 P/D。

本轮作业：P/D allocation 为 6386；原有数据回放为 6387；受控矩阵为 6388。
矩阵通过 `afterok:6387` 依赖保证不会与原有数据实验重叠。

## 统计口径与解释边界

- **主要结果**：每个单元 early / finish-only 的交接 P90/P95；P99 附带报告。
- **机制证据**：P finish 前已完成的字节/块数、D finalize 时接收水位、最终
  传输字节数和最终批次 NIXL duration。
- **代价检查**：finish 到 P 首 token、完整响应耗时、全部请求成功率与正式
  配对人数，不能只看成功请求的加速。
- **重复轮次**：先分别计算每轮分位数，再报告其间中位数及最小/最大范围。
  重复范围不是置信区间，也不把两轮延迟池化后称为一个 P99。
- **共同样本**：延迟对照只采用两边完整成功、统计有效且有 D 输出的共同
  请求。超时、无 D 输出等仍计入全量人数；失败较多的单元不能据此宣称尾部
  延迟改善，因为排除失败会产生选择偏差。
- **跨场景归因**：增加 Append 会同时降低 Update 重算量。三个场景的原始
  时延差不是提前传输的纯因果效应；优化收益必须首先比较同场景内部的 A/B。
- **传输量**：总字节数不因提前发送而减少，减少的是 finish 阶段剩余字节。
  提前批次字节数也不等价于 finish 前已经完成的字节数。
- **传输耗时**：`final_transfer_ms` 为多个 WRITE duration 的累计值，重叠
  传输时不等于最终等待墙钟时间。

在没有抢占和 Update 合并时，5 个等长 Update 版本的名义新计算量为
`U + 4 × (U − LCP) = 2U`。因此三个场景的知识累计 prefill 量分别为
3840、3072、2304 tokens，而不是都等于最终知识长度 2048。这里还没有计入
模板、question 和 padding 的计算；两个 Append work 追加时也会重写原来的
尾部 padding。同场景的 early / finish-only 使用完全相同的这些输入和计算。

## 结果汇总

### 原有数据的第一轮

128 个样本在两种模式中全部完成，128 对均有实际 D 输出且统计有效。

| 指标 | finish-only | 提前 Push |
| --- | ---: | ---: |
| P→D 交接 P90 | 305.8 ms | 273.8 ms |
| P→D 交接 P95 | 309.9 ms | 274.5 ms |
| P→D 交接 P99 | 317.3 ms | 276.7 ms |
| 最终 NIXL WRITE duration 累计值 P95 | 184.8 ms | 145.8 ms |
| finish→P 首 token P95 | 159.5 ms | 169.2 ms |
| P finish 前已完成字节占总字节的平均比例 | 0% | 14.8% |
| 请求成功率 / 正式配对 | 100% / 128 | 100% / 128 |

这一轮交接 P90/P95 分别下降约 10.5% / 11.4%，但 P 首 token 的 P95
增加约 9.7 ms。

### 原有数据的第二轮

交换 A/B 顺序后，仍有完整的 128 对正式样本，两组请求成功率均为 100%。

| 指标 | finish-only | 提前 Push |
| --- | ---: | ---: |
| P→D 交接 P90 | 311.6 ms | 273.1 ms |
| P→D 交接 P95 | 314.2 ms | 274.3 ms |
| P→D 交接 P99 | 318.1 ms | 279.4 ms |
| 最终 NIXL WRITE duration 累计值 P95 | 186.8 ms | 146.1 ms |
| finish→P 首 token P95 | 164.3 ms | 164.5 ms |

两轮交接 P95 分别改善约 11.4% / 12.7%，最终 WRITE duration P95
改善约 21.1% / 21.8%。P 首 token 的 P95 没有稳定的改善，第一轮略增、
第二轮基本相同。因此目前结论限定为：**这个数据和顺序负载下，提前传输
可稳定缩短 P→D 交接，而不是使 P 本身的首 token 更快。**

### 受控矩阵的完成情况

三个占比与三个 QPS 组成 9 个单元，每单元两轮；已完成全部 18 组 A/B。
受控矩阵共提交 4608 次请求，4607 次完整成功且统计有效：early 为
2304/2304，finish-only 为 2303/2304。正式共同配对为 2303 对，
即有 4606 条响应进入共同样本延迟对照；另有一条 early 成功响应因对照失败
而不进入配对，但仍保留在全量成功/正式人数中。

唯一失败发生在 **50% 稳定占比、QPS=1、第一轮 finish-only** 的
`anns-query-000028`：start 收到 HTTP 502，上游操作为 D 的
`/stable_kv/reserve`，错误内容为空。该轮 finish-only 为 127/128，
early 为 128/128，正式共同配对为 127 条；其余 17 组 A/B 均有
128 对。不能仅凭空错误内容认定是显存、超时或 NIXL 的某个具体故障，
也不能删掉这条失败来报告整个实验 100% 成功。

原有性能集 512 次提交全部成功，形成两轮各 128 对；加上受控矩阵，
本轮共提交 5120 次正式测量请求，5119 次成功，预热均不计入。
重复轮次使用相同编号样本；上述请求数量不是 5120 个不同问题。

### 受控矩阵的交接尾延迟

下表每格均为 **finish-only → early push**，单位 ms。每个数先在一轮
共同成功样本上计算分位数，再取两轮分位数的中位数；没有池化两轮延迟。
P95 降幅也按这两个汇总值计算，正值表示更快，负值表示退化。

| 稳定知识占比 | QPS | 交接 P90 | 交接 P95 | 交接 P99 | P95 降幅 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 12.5% | 0 | 325.1 → 300.6 | 326.4 → 302.1 | 329.3 → 303.9 | 7.43% |
| 12.5% | 1 | 536.2 → 495.6 | 612.9 → 564.4 | 755.7 → 695.5 | 7.91% |
| 12.5% | 2 | 642.8 → 647.6 | 696.9 → 697.6 | 745.0 → 810.1 | −0.11% |
| 50% | 0 | 326.0 → 229.7 | 327.2 → 231.6 | 329.8 → 233.0 | 29.22% |
| 50% | 1 | 523.1 → 410.3 | 574.7 → 462.8 | 840.0 → 535.2 | 19.47% |
| 50% | 2 | 691.0 → 508.9 | 766.8 → 541.7 | 835.1 → 613.0 | 29.35% |
| 87.5% | 0 | 326.6 → 158.1 | 328.2 → 159.1 | 329.5 → 160.8 | 51.52% |
| 87.5% | 1 | 506.5 → 369.6 | 548.7 → 399.4 | 702.2 → 482.7 | 27.22% |
| 87.5% | 2 | 601.6 → 469.8 | 645.2 → 511.1 | 697.4 → 665.3 | 20.79% |

QPS=0 时，交接改善随稳定占比增大而明显增加。负载升高后，不再是占比越高
就保证更大的端到端收益：12.5%、QPS=2 的两轮交接 P95 分别改善 5.75%
和退化 6.23%，汇总后基本持平，P99 变差。每轮只有约 128 条配对样本，
P99 主要由极少数最慢请求决定，不能当作稳定极端尾部结论。

### 客户端实际等待与 P 首 token 的代价

客户端收到的第一个 token 来自 P。`finish_to_d_first_client_ms` 表示
提交 finish 到收到第一个 **D 续写 token** 的实际时间，不是常规 TTFT。
`finish_to_p_first_client_ms` 才表示此路径客户端的首 token 等待。
`finish_to_done_ms` 表示完整响应结束时间。这三个指标均直接从客户端
时间戳计算，**没有将 P 首 token P95 与交接 P95 相加**。

下表仍是两轮分位数中位数，数值方向和单位与上表相同：

| 稳定知识占比 | QPS | finish→D 续写 P95 | D 续写等待降幅 | finish→P 首 token P95 | 完整响应 P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 12.5% | 0 | 415.2 → 391.7 | 5.68% | 93.7 → 94.2 | 2080.6 → 2058.4 |
| 12.5% | 1 | 1019.5 → 1105.5 | −8.44% | 500.2 → 510.2 | 2876.8 → 2863.3 |
| 12.5% | 2 | 1310.2 → 1312.2 | −0.16% | 781.7 → 805.1 | 3323.0 → 3265.7 |
| 50% | 0 | 426.1 → 329.5 | 22.67% | 103.0 → 103.2 | 2111.6 → 2013.0 |
| 50% | 1 | 881.8 → 848.4 | 3.79% | 335.2 → 414.3 | 2683.5 → 2620.5 |
| 50% | 2 | 1209.9 → 1109.5 | 8.30% | 551.8 → 677.4 | 3035.4 → 3002.5 |
| 87.5% | 0 | 433.0 → 263.7 | 39.10% | 109.1 → 109.6 | 2126.9 → 1958.0 |
| 87.5% | 1 | 774.8 → 831.5 | −7.32% | 301.8 → 425.2 | 2569.5 → 2619.3 |
| 87.5% | 2 | 988.6 → 1156.2 | −16.95% | 492.9 → 756.6 | 2881.8 → 3078.6 |

**交接阶段改善可以与整体退化同时发生。** 例如 87.5%、QPS=2 的交接
P95 减少 20.79%，但 P 首 token P95 增加约 263.7 ms，客户端等待 D
续写的 P95 增加 16.95%，完整响应 P95 增加 6.83%。50%、QPS=1/2
虽然客户端等待 D 的 P95 仍减少，但收益小于交接阶段的降幅。

这些数值说明本轮实现的提前传输存在负载相关代价，不能据此宣称全负载无代价
加速。提前 WRITE、控制处理与 GPU 可见性同步等是后续可检查的路径，
但本轮没有做对应消融，不能将观测到的 P 退化归因于其中一个已确定的根因。

### 提前完成水位与剩余传输量

受控请求每条的总传输量为 **74.8125 MiB**，两种模式相同。下表的最终
传输量与提前完成比例均由逐请求统计取得；先算每轮均值，再取两轮中位数。
因 QPS=1、50% 的共同样本排除了一条失败，均值有极小差别，表中按两位
小数展示，不将其当作传输内容改变。

| 稳定知识占比 | QPS | 最终 WRITE 字节，MiB | P finish 前实际完成字节比例 | 最终 WRITE duration 累计值 P95，ms |
| --- | ---: | ---: | ---: | ---: |
| 12.5% | 0 | 74.81 → 64.61 | 0% → 13.64% | 195.2 → 169.2 |
| 12.5% | 1 | 74.81 → 64.61 | 0% → 13.64% | 292.1 → 257.4 |
| 12.5% | 2 | 74.81 → 64.61 | 0% → 13.59% | 291.6 → 295.8 |
| 50% | 0 | 74.81 → 37.61 | 0% → 49.73% | 195.9 → 99.6 |
| 50% | 1 | 74.81 → 37.61 | 0% → 49.73% | 308.3 → 170.8 |
| 50% | 2 | 74.81 → 37.61 | 0% → 49.73% | 326.8 → 208.1 |
| 87.5% | 0 | 74.81 → 10.61 | 0% → 85.82% | 196.0 → 28.1 |
| 87.5% | 1 | 74.81 → 10.61 | 0% → 85.82% | 295.2 → 113.9 |
| 87.5% | 2 | 74.81 → 10.61 | 0% → 85.82% | 312.7 → 185.2 |

三种占比的 early 最终传输量相对对照减少约 13.64%、49.73%、85.82%。
实际提前完成比例与知识占比不是同一个分母：传输包括模板、question 与整块
布局，提前发送又要求 Prefix+Append 的完整稳定块，因此比例不要求完全相等。
这部分实际完成字节已移出最终阶段，但不等价于隐藏了相同比例的端到端时间。

12.5%、QPS=2 的 P 主线程提前完成水位约为 18.08 块，而 D finalize 时
已收到约 18.14 块，体现了完成回报的保守性；其他单元 P/D 平均水位接近，
50% 与 87.5% 分别约为 66.14 与 114.14 块。即使最终传输字节减少，
高负载下最终 WRITE duration 的累计值也仍可能上升。

### 本轮能够支持的结论

- 稳定 KV 的提前发送与最终收养可以在完整 P/D 生成链路上工作；本轮
  受控矩阵 4608 次提交中 4607 次完整成功，唯一 reserve 502 仍在分母中。
- 在本轮同主机 A30 双卡的三个顺序负载场景中，提前完成比例更高的场景
  剩余传输量更小，P→D 交接 P95 改善由约 7.4% 增至约 51.5%，
  客户端等待 D 续写也改善；这不是对任意负载的单调性保证。
- 在 QPS=1/2 下，交接通常仍可缩短，但 P 等待会增加，客户端等待 D 续写
  与完整响应并非普遍变快；不能只用交接时延宣称总体收益。
- 本轮是单模型、同主机双卡与单一来源节奏的性能对照，不代表跨主机网络、
  更大 GPU、其它模型或所有更新时序。两轮范围不是置信区间，未做显著性检验。
- 合成输入没有标准答案，本轮不提供问答质量结论，也不从输出能完成推导
  近似计算质量无损；性能实验与此前 SQuAD 质量实验是不同证据。

## 实现验证与运行审计

本轮最终 6 个 CPU 测试文件共 100 项通过；相关 Python Ruff 检查、shell
语法检查和 diff 空白检查通过。P95 八面板已检查，用户 D 续写等待与 P 首
token 的退化没有被阶段指标隐藏。

运行审计保留 5120 次正式提交中的 1 次 reserve 502，未发现统计无效响应。
原有与受控场景合计有 2559 对正式共同样本。原有顺序负载的 256 对与
受控 QPS=0 的 768 对，完整输出 token 序列分别全部一致；这里只作为
这几组传输路径的回归观察，不等于标准答案正确率，也不保证竞争调度下
所有请求始终输出完全相同。

日志未发现抢占、运行期 OOM 或受控正式阶段的新增 JIT 警告。因此本轮
负载下的整体退化不能直接解释为抢占导致，具体开销仍需消融定位。
结束后已释放本轮 P/D、proxy 与回放资源，没有继续占用服务端 GPU。

配套命令与输出字段见 [README.md](README.md)。

随后对高稳定占比、QPS=2 做了短区间 nsys 排查。显式 DeviceSynchronize
累计不足 0.2 ms，更明显的证据是大量 8 KiB D2H 搬运与长时间模型提交
重叠。该诊断有工具开销、没有替换本页的正式结果，详细证据与限制见
[nsys 排查记录](nsys/README.md)。
